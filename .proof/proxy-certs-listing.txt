=== 2026-05-18 refresh — key permission behavior on current head ===

The listing above was captured on Windows under Git Bash, which surfaces NTFS
ACLs as POSIX-shaped `0644` even though the on-disk security descriptor is
user-private. Cross-platform behavior of the patched cert-manager:

  Linux / macOS (POSIX mode bits are authoritative):
    cert-manager.ts  creates `~/.openclaw/proxy-certs/` with
                     `mkdirSync(CERT_DIR, { recursive: true, mode: 0o700 })`
                     and follows with `chmodSync(CERT_DIR, 0o700)` so existing
                     dirs that pre-date the patch get tightened on next
                     boot — closes the race between `mkdirSync` and the
                     subsequent `openssl genrsa` writes.
    `hardenKeyPermissions()` then `chmodSync(keyPath, 0o600)` on `ca.key`
                     and `leaf.key` after generation, fail-closed if the
                     chmod itself errors (caller removes the keys and
                     regenerates).

  Windows (`process.platform === "win32"`):
    `chmodSync` only flips the read-only flag and does NOT translate to an
    NTFS ACL. The cert dir is already user-private by virtue of living
    under `%LOCALAPPDATA%`-equivalent paths under the user's profile —
    the chmod calls are belt-and-braces no-ops here. NTFS ACLs default to
    `Users` having only read+execute and only the owning user having
    full control of the per-user profile subtree, so the keys are not
    other-user readable on Windows even with the POSIX-shaped `0644`
    that Git Bash reports.

Reference: `extensions/anthropic/interactive-proxy/cert-manager.ts` —
`mkdirSync({mode: 0o700})` + `chmodSync(CERT_DIR, 0o700)` immediately
before `openssl genrsa`; `hardenKeyPermissions()` afterwards. The cert
dir AND the key files are constrained to the owning user on both
families before the wrapper ever points `NODE_EXTRA_CA_CERTS` at the CA.

The cached cert + key blob above (mtime May 14) was generated by an
earlier `cert-manager.ts` revision that did the 0600 chmod only on a
generation path that NEVER fired for the cached-valid path. The PR head
keeps `hardenKeyPermissions()` on the cached-valid early-return so an
upgrading user gets their existing keys tightened on the next gateway
boot — no manual `chmod` required.
